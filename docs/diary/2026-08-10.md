## なぜ / 判断

- **「無限に追加し続ける」をそのまま実装すると壊れる**ので、
  *維持コストをループ回数×1で逓増*させ、手番開始時に払えなくなったら自動で切れる設計にした。
  上限8ループも入れて、終息を保証する（設計として「止まらない」状態を作らない）。
- 全軍突撃（3ターン固定）との差別化は「**期間が固定か、資源が続く限りか**」に置いた。
- 追加物を*コマとアイテムの交互*にしたのは、要望が「アイテムやキャラ」だったのに加え、
  **毎回バッズを植てると魔力収入が維持コストと相殺されて本当に無限になる**ため。
  交互なら バッズ ≈ ループ数/2 < 維持コスト = ループ数 で必ず先細りする。
- ノブを `sim/config.js` に出したのは、`/balance-loop` からコード変更なしで回せるようにするため。
  ただし **src 側の定数と二重管理**になっている（README と balance-loop skill に同期の注意を明記）。
- コスト当初7では **AI 発動率 0.3%** で死にスキルだった。撃たれないスキルは調整もできないので
  6 に下げ、AI の発動条件も「コスト+4の余裕」→「+1」に緩めた（発動率 4.3%、平均2.6ループ）。

- master CI: 一度 **失敗** → 修正後 success。公開サイト HTTP 200。

### 反省（同じ失敗を繰り返さないため）
**master を一度赤くした。** 原因は `tsconfig` の `jsx: "react"`（classic）で、
`.tsx` には `import React` が必要なのに省いたこと。jest は babel 経由なので通るが、
本番ビルドの型チェック（fork-ts-checker）が TS2686 で落ちる。

検証手順の穴が2つあった:
1. `tsc --noEmit` を**新ファイルを作る前**に流していた（＝新ファイルを検証していない）
2. PR にチェックが走らないので、master に入るまで気づけなかった → issue #5

以後、テストやコンポーネントを追加したら **追加後に** `tsc --noEmit` と
`react-scripts build` の両方を流す。

## 23:20 loop iteration 2 — PR に CI チェックを出す (issue #5)

### やったこと
- `.github/workflows/deploy.yml` を **test / deploy の2ジョブに分割**
  - `test`: `pull_request` でも走る（sim テスト + jest + 本番ビルド=型チェック）
  - `deploy`: `needs: test` かつ master への push のときだけ
  - concurrency は PR なら古い実行をキャンセル、master は直列化
- PR #6 で検証してマージ

### なぜ / 判断
- **書いたルールでは #5 は「その他の改善」で優先度4**。それを飛ばして最優先にした理由は、
  この欠落が iteration 1 で **実際に master を赤くした直接原因**だから。
  「安全網そのものが壊れている」は、次のイテレーション全部の失敗率に効くので先に直す。
- ブランチ保護（`test` を必須チェック化）は**今回は入れなかった**。
  設定を誤るとループ自身が master に push できなくなり、事故時の復旧が遅れる。
  必要になったら issue #5 のコメントに置いたコマンドで後から入れられる。
- `build`（型チェック）を test ジョブに残したのが肝。iteration 1 の TS2686 は
  **jest では拾えない**（babel 経由なので型を見ない）。落とすなら本番ビルドしかない。

- PR #6: `test` **pass (34s)** / `deploy` **skipping** ← 意図どおり
- master: `test` **success** / `deploy` **success**、サイト HTTP 200
- 実証: iteration 1 で master に入ってしまった TS2686 は、この構成なら PR で止まる
