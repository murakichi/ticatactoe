# バランス分析レポート

ヘッドレスエンジン（`sim/engine.js`, 実ゲームロジックの忠実移植）で AI 対 AI を多数試行した結果と、
ソース精読で判明した構造的バランス問題。

実行例:
```
node sim/cli.js sim --games 2000 --mode faithful   # 全6キャラ総当たり
node sim/cli.js sim --games 3000 --pair giant,you  # 特定マッチアップ
node sim/cli.js auto --hchar giant --cchar you      # 1試合を観戦
```

## 定量結果（faithful AI = 実装の AIPlayer.ts と同一挙動 / 2000試合/組）

### 先手・後手
| | 勝率 |
|---|---|
| 先手 💙 | 15.6% |
| 後手 ⭕ | 12.9% |
| 引き分け | **71.5%** |

- **引き分けが約7割**。勝ち/ブロックだけの AI と 4x4・4目並べでは決着が付きにくい。
- 先手有利は +約3pt（小さいが一貫）。

### キャラ別勝率（引き分け除外, wins/(wins+losses)）
| キャラ | 先手 | 後手 | 総合 |
|---|---|---|---|
| you | 91.8% | 82.9% | 87.5% |
| tactician（軍師） | 91.0% | 82.4% | 86.9% |
| magician（魔法使い） | 90.6% | 82.1% | 86.6% |
| **giant（巨人）** | **0.8%** | **0.3%** | **0.6%** |
| yinYangMaster（陰陽師） | 91.2% | 82.6% | 87.1% |
| necromancer | 91.2% | 82.9% | 87.2% |

- **giant 以外は統計的に同一**（87%前後、誤差範囲）。
- 非giant同士の直接対決は約95%が引き分け（例: you vs you=94.7%、tactician vs magician=93.6%）。
  → 高い総合勝率はすべて「giantを一方的に倒す」ことに由来。
- **giant は対AIで勝率ほぼ0%**（giant vs you 3000試合: giantの勝ち **0.0%**）。

## 根本原因（ソース精読で判明）

1. **AIのスキルが完全な無効動作**
   `AIPlayer.useSkill` は `skillCallback` を呼ぶが、Game.tsx 側の
   `useSkillForHeart/Circle` は `setMagic(prev - cost)` するだけで、スキル本体
   （`onClickToken` 等）を一切実行しない。→ AIは「マジックを捨てるだけ」。
   このため**キャラ固有スキルが対AIでまったく機能せず、キャラ差が消える**。

2. **巨人の手番スキップが一方的不利**
   `judgeNextIsHeart` の giant 分岐で巨人は約2手に1手しか打てない。
   ライフ3倍（=bind）は、AIが**捕獲手を選ばない**ため活きない
   （`getBestMove` は空きマスのみ対象）。手数だけ減って負ける。

3. **bind が 0 になっても記号が残る（駒の永続化）**
   decay処理 (`onCellClick`) は bind を減らすが player は消さない。勝利判定は
   記号のみ。→ ライフ/bind は AI 戦の勝敗にほぼ無関係。素の4目並べ化。

4. **マジック付与のバグ**（`Game.tsx:102`）
   後手（円）の次マジックを `heartMagic` と heart の buds から計算している
   （`nextMagic = heartMagic + 1 + budsCount('💙')`）。後手のマジックが先手の
   状態に依存する。本エンジンは正しい挙動（各プレイヤー自身の値）で実装し、
   ここで明示。

5. **未実装スキル**: `onClickNecromancy` / `onClickUnlock` は空関数。
   ネクロマンサーの蘇生はUI上存在するが効果なし。

## 改善提案（バランス調整の方向性）

- **AIにスキルを実行させる**: `useSkillCallback` に実スキル関数を渡す（最優先。
  これだけでキャラ差が初めて意味を持つ）。
- **AIに捕獲手を評価させる**: `getBestMove` で占有マスの捕獲による勝ち/ブロック
  も探索（`--mode capture` で実験可能。giant勝率 0.6%→11.5% に改善）。
- **巨人**: 手番スキップが重すぎる。ライフ3倍を活かす捕獲AI前提に再調整、
  またはスキップ頻度を緩和。
- **引き分け過多**: 先手有利を強める/盤面を変える、または bind 0 の駒を
  「弱体化（捕獲容易）」扱いにして終盤の決着性を上げる。

### iter7 結果（最終採用）
`giantSkipModulo: 5` + `giant life mean: 8` + modulo ロジック修正:
```javascript
// 旧: 2条件で判定 → modulo値が変わると比率が崩壊
// 新: currentTurn % mod < mod - 1 → allow, else → skip
if (s.currentTurn % mod < mod - 1) return !s.heartTurn;
return s.heartTurn;
```
mod=5 で巨人は5手中4手プレイ（80%の頻度）。mod=3（元）は3手中2手（67%）。

## 改善ループ Phase 3.1（巨人ナーフ手段の見直し: ライフ→オフェンス, faithful 400試合）

**動機:** Phase3 iter1 で巨人を life8→7 にナーフしたが、これは巨人の「タンク（高ライフ）」
アイデンティティを削ってしまう。**ナーフはオフェンス/テンポ側に寄せ、ライフは高く保つ**べき、
という方針で再検証した。

| tag | giant勝率 | giantGap | 巨人の中身 | 判定 |
|---|---|---|---|---|
| Phase3-iter2（基準: life7, +魔力, mod5） | 0.573 | −0.088 | 薄いタンク | — |
| life7→8 復元のみ（+魔力, mod5） | 0.645 | −0.174 | 厚いが強すぎ | ❌ 単独では過剰 |
| life8 + giantSkipModulo 5→4 | **0.876** | **−0.451** | 暴走 | ❌❌ modは非単調/逆効果 |
| **life8 + 毎ターン+1魔力を撤廃** | **0.499** | **+0.002** | **厚いタンク・低テンポ** | ✅ **採用** |

### 結論
- **`giantSkipModulo` は使えない**: 5→4（スキップ増＝弱くなるはず）が逆に giant を
  0.645→0.876 に**強化**した。modulo ロジックは非単調で信頼できない（旧ログ
  「iter6-mod4: 逆効果」と整合）。テンポ調整の手段としては不採用、5 のまま据え置き。
- **採用案: 巨人を `magicCharacter` から外す**（毎ターンの魔力+1を撤廃）。
  ライフは 8 に復元（タンク特性を維持）、代わりに魔力供給を絞ってストンプの頻度を下げる
  ＝**ボディではなくエンジンをナーフ**。giantGap −0.088→**+0.002**（ほぼ完全均衡、
  iter2 より良化）。他指標は退化なし（spread 0.225≈iter2 0.227、firstAdvantage は
  4x4 構造由来の既知課題で原因不変）。
- 副産物バグ修正: `src/util.ts` の giant life mean が **10**（sim=8 と乖離）だった→ 8 に同期。

## 新スキル「増殖」(ループ召喚) の導入と影響計測

**コンセプト:** 「ループでアイテムやキャラを追加し続ける」スキル。既存の全軍突撃（3ターン
固定）と違い、**払える限り無限に続く**代わりに**維持コストが毎ループ +1 逓増**して自己終息する。

| 項目 | 値 | 置き場所 |
|---|---|---|
| 発動コスト | 6 | `skillCosts.onClickProliferate` / `sim/config.js: proliferate.cost` |
| 追加コマのライフ | 2 | `Game.tsx proliferateTokenLife` / `proliferate.tokenLife` |
| 維持コスト増分 | +1/ループ | `proliferateUpkeepStep` / `proliferate.upkeepStep` |
| 打ち止め | 8ループ | `proliferateMaxStacks` / `proliferate.maxStacks` |

- 発動後、**自分が着手するたび**に 奇数回=コマ(ライフ2)、偶数回=アイテム(🌱 / 毒使いは敵に☠)
  を交互に1つ追加。追加できない（空きマス無し等）ならループ回数を進めない。
- **手番開始時**に `ループ回数 × 1` の維持コストを支払う。払えなければその場でループ終了。
  → 4ループ回すと累計 6+1+2+3 = 12 マジック。バッズが生む魔力で一部は自弁できる。
- スキルプールは 0–19 → **0–20** に拡張（`reshuffledSkills(21, …)` / `reshuffleSkillsFor(…, 21)`）。

### A/B 計測（faithful, 8試合/組 × 49組 = 392試合, seed 1）

`proliferate.cost` を 999 にして AI が撃てない状態を対照群にした。

| tag | drawRate | firstAdvantage | nonGiantSpread | giantGap | avgTurns |
|---|---|---|---|---|---|
| 増殖あり | 0.000 | 0.281 | **0.304** | 0.031 | 14.6 |
| 増殖なし | 0.000 | 0.260 | **0.304** | 0.010 | 14.7 |

キャラ別勝率の差は 魔法使い +0.018 / 巨人 −0.018、他は完全同値。**spread は不変**で、
この試行数では有意差なし＝現行コストではバランスを壊していない。

### 監視ポイント
- **AIの発動率**は 1手番あたり約4%（手札に来る 3/21 × マジック7以上）。ノブを動かした後は
  発動率も併せて確認しないと「効果が出ない＝撃っていないだけ」を見誤る。

### 追試: ループは終息するか（2026-08-11, issue #1）

「偶数ループのバッズが魔法使いの魔力（自陣バッズ1個=+3）を養い、維持コストを上回って
**ループが終わらなくなる**」という懸念を検証した。勝率では発動率4%のせいでシグナルが乗らない
ため、**最初に払える手番で強制発動させ、ループ到達回数を直接測る**統制実験に切り替えた
（`node sim/probe-proliferate.js [n]`、n=60/側 → 1キャラあたり最大120試合）。

| キャラ | 発動到達% | 平均ループ数 | 上限(8)到達% |
|---|---|---|---|
| you | 53% | 2.49 | **0.0%** |
| 軍師 | 8% | 1.78 | **0.0%** |
| **魔法使い** | 98% | **4.40** | **0.0%** |
| 巨人 | 28% | 1.91 | **0.0%** |
| 陰陽師 | 94% | 3.98 | **0.0%** |
| ネクロマンサー | 53% | 2.48 | **0.0%** |
| 毒使い | 7% | 1.88 | **0.0%** |

**結論: 懸念は棄却。** 全キャラ・全試行で上限8に到達せず、ループは必ず維持コスト切れで
終息した。魔法使いは他平均の約1.8倍(4.40 vs 2.42)続くが、**有限**。勝率A/B(392試合)でも
+0.018＝誤差範囲だったため、**ナーフは見送り**（`upkeepStep` は 1 のまま）。
バッズ→魔力が魔法使いのアイデンティティである以上、増殖が長く回るのは設計どおりの強みと判断。

副次的発見:
- **陰陽師も長い(3.98)**。陰モードの毎ターン魔力+1が効いており、魔法使いだけの問題ではない。
- 軍師(8%)・毒使い(7%)の発動到達率が極端に低いのは、非トークン/非毒スキルへのコスト修正
  (+2/+1)で発動コストが8/7になるため。**この2キャラは増殖をほぼ使えない**＝実質的に
  キャラ間で使用可否が分かれている。強さの問題ではないが、設計意図として要確認。
