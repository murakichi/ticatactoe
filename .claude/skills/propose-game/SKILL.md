# propose-game — スキル/キャラを提案して起票する

**ここでやるのは提案と起票まで。実装はしない。**
起票した issue は `/diary-improve-loop` が1件ずつ拾って実装・計測・記録する。
この分業を守ること（提案と実装を同じセッションで混ぜると、採用基準が「実装しやすさ」に歪む）。

## 0. 大前提 — 追加は必ず6箇所に波及する

新スキル/新キャラを1つ足すと、最低でも次を全部触ることになる。
**提案の時点でこの分量を見込む**（見込めない案は issue にしない）。

| 層 | ファイル | 何を足すか |
| --- | --- | --- |
| コスト | `src/components/game/skillCosts.ts` | `onClickXxx: N` |
| ゲーム本体 | `src/components/game/Game.tsx` | 状態・`exeXxx`/`onClickXxx`・スキルカード(idx)・リスタート時のリセット |
| 演出 | `src/components/game/BoardEffects.tsx` (+`.module.css`) | エフェクト種別 |
| AI | `src/components/game/AIPlayer.ts` | 発動条件ゲート・`chooseLocks` の `case`・idx上限 |
| sim | `sim/engine.js` / `sim/ai.js` / `sim/config.js` | 上記の忠実移植＋調整ノブ |
| 検証/記録 | `sim/engine.test.js` / `docs/characters.md` / `src/App.tsx` | テスト・資料・キャラ説明文 |

`増殖`(idx 20) が全層に入った実例なので、**`grep -rn "増殖" src sim` で触るべき場所を洗い出せる**。
新キャラなら `src/types/Character.ts` の `CharacterId`、`src/util.ts` の `LIFE_MEANS`、
`sim/config.js` の `lifeMeans` も追加対象。

## 1. 現状を読む（ネタ出しの前に必ず）

```bash
gh issue list --state all --limit 50        # ← closed も見る。却下済みの案を再提案しない
cat docs/characters.md                       # キャラのコンセプトと21スキル一覧
cat src/components/game/skillCosts.ts        # コスト帯の分布
git log --oneline -15
```

**closed issue を読むのがこのステップの主目的**。過去に「仕様」「有意差なし」で閉じた案を
言い換えて出し直すのが一番ありがちな失敗。

## 2. 空白を探す（思いつきで出さない）

案は「面白そう」から出さず、**埋まっていないマス**から出す。次の3軸で現状を表にする。

- **効果カテゴリ**: 配置 / 除去 / ライフ操作 / 経済(魔力) / 妨害(🔑ロック) / 継続効果(🌱☠) / 反応(トリガ型)
- **コスト帯**: 1-3(小回り) / 4-6(主力) / 7-9(切り札) / 10+(勝負手)
- **受益キャラ**: 誰が得をするか。**どのキャラも得をしていない軸**があればそこが空白

キャラ案の場合は「既存6キャラのどれとも違うリソースを持つか」で見る
（軍師=トークン、魔法使い=バッズ経済、巨人=ライフ、陰陽師=モード、ネクロ=墓地、毒使い=継続毒）。
**既存の焼き直しになる案は落とす**。

計測で裏を取れるならそのほうが強い。ただし現状 `sim/cli.js metrics` に
**スキル別使用率の出力は無い**ので、死にスキルを根拠にしたいときは
`sim/probe-proliferate.js` を雛形に単発の計測スクリプトを作ること（推測で「使われていない」と書かない）。

## 3. 採用基準 — 全部 ✅ でなければ issue にしない

1. **既存プリミティブで表現できる**か
   （`bind` / `effects: 🌱🔑☠` / `magic` / トークン / 手番）。
   新しい状態次元を増やす案は、それ自体を1つの issue にして先に議論する
2. **AI が使えるか**。`AIPlayer.ts` の評価関数で価値を判定できない効果は、
   実装しても発動率が数%に張り付いて死にスキルになる（増殖で実測済み）。
   *「AI はどういう条件でこれを撃つか」を1文で書けること*
3. **自己終息するか**。無限に増える/永久に詰む効果は、
   維持コスト逓増や上限で必ず収束させる設計を添える
4. **測れるか**。勝率は発動率が低いと信号にならない。
   **機構レベルの指標**（発動率・平均効果量・上限到達率など）を1つ定義できること
5. **既存キャラのアイデンティティを壊さないか**。
   例: 全キャラが撃てる汎用スキルで毒を撒けるなら、毒使いの固有性が薄まる

落とした案も**理由つきで手元に残す**（提案時に「検討したが落とした案」として提示する）。

## 4. 提示 → 起票

1. **3〜5案を並べて提示**する。1案あたり: 名前 / 効果1〜2行 / コスト帯 / 受益キャラ / 埋める空白 / 基準4の測定指標
2. **どれを起票するかユーザーに確認する**（案の良し悪しは好みが入るため、勝手に決めない）
3. `/loop` など非対話で呼ばれた場合のみ、**最も基準を満たす1件だけ**を自動で起票する
4. **一度に積むのは最大2件**。`/diary-improve-loop` は1イテレーション1件しか消費しないので、
   積みすぎると古い案が腐る

```bash
gh issue create --title "<スキル名/キャラ名>: <一言でわかる効果>" --label "proposal" --body "$(cat <<'EOF'
## 提案
（効果を2〜3行。コストの初期値も書く）

## 埋める空白
（効果カテゴリ / コスト帯 / 受益キャラ のどこが空いているか。計測したなら数値を添える）

## AI の発動条件（案）
（AIPlayer.ts でどう判定させるか。ここが書けない案は起票しない）

## 収束の担保
（無限化・詰みを防ぐ仕組み。該当しないなら「不要（単発効果）」と書く）

## 検証方法
- 指標: （発動率 / 平均効果量 / 勝率差 など）
- コマンド: `node sim/cli.js metrics --games 800 --seed 1`
  （機構レベルで測るなら sim/probe-*.js を追加する）

## 実装チェックリスト
- [ ] `src/components/game/skillCosts.ts`
- [ ] `src/components/game/Game.tsx`（状態 / 実行 / スキルカード / リスタート時リセット）
- [ ] `src/components/game/BoardEffects.tsx` + `.module.css`
- [ ] `src/components/game/AIPlayer.ts`（発動ゲート / chooseLocks / idx上限）
- [ ] `sim/engine.js`・`sim/ai.js`・`sim/config.js`（ノブ追加）
- [ ] `sim/engine.test.js` にテスト追加
- [ ] `docs/characters.md` と `src/App.tsx` の説明文を更新
- [ ] `node sim/engine.test.js` / `npx tsc --noEmit` / `npm test -- --watchAll=false`

## 却下条件
（「発動率 <3% なら不採用」のように、**先に**引き際を決めておく）
EOF
)"
```

`proposal` ラベルが無ければ作る:
```bash
gh label create proposal --color "c2e0c6" --description "スキル/キャラの新規提案"
```

## 5. 仕上げ

- 起票したら `/work-diary` で日記に1エントリ（**なぜその空白を選んだか**と、落とした案の理由）
- 日記の `## 積み残し` に `- [ ] <案> — issue #N` を残す

## やってはいけないこと

- このスキルで実装を始める（提案と実装を分ける意味が消える）
- closed issue を確認せずにネタ出しする
- 「AI がどう撃つか」を書かずに起票する（死にスキルの直行便）
- 一度に5件も6件も積む
- 計測していないのに「今この軸は使われていない」と書く
