# work-diary — 作業日記を書く

作業のまとまりが終わったら、**必ず**このスキルで日記を1エントリ書く。
「あとでまとめて」は禁止（測定値と判断理由は時間が経つと再現できない）。

## 1. 何を書くか

`docs/diary/YYYY-MM-DD.md`（Obsidian vault。同日2回目以降は同じファイルに `## HH:MM <題>` で追記）。

```markdown
---
date: YYYY-MM-DD
tags: [diary]
issues: [12, 13]     # このエントリで立てた/進めた issue 番号
---

# YYYY-MM-DD

## やったこと
- 1行1件。**成果物のパス**を必ず添える

## なぜ / 判断
- 選ばなかった案と、その理由。ここが日記の本体
- 「無限に追加できると壊れるので維持コストを逓増させた」のような設計判断を残す

## 計測
- 試合数 / seed / 指標を数値で。A/B したら対照群も
- 「測っていない」なら **測っていないと書く**（後で誤読しないため）

## 積み残し
- [ ] 内容 — issue #12
```

### 書き方の原則
- **git log と diff が持っている情報は書かない**（ファイル一覧・行数・関数名の羅列は不要）。
- 残すのは **判断・数値・次の一手**。3か月後の自分が同じ結論に到達できるか、で判断する。
- 関連エントリは `[[2026-08-10]]` でリンクする。書いたら `docs/diary/README.md` の
  「エントリ」一覧にも1行足す。

## 1.5 回帰テストを書いたら「落ちること」を確認する

バグ修正に回帰テストを添えたら、**修正を一時的に戻してテストが落ちるところまで見る**。
通ることしか確認していないテストは、実は前提が成立せず空振りしている場合がある
（例: 「⭕が陽のとき〜」を検証するテストが、バグで⭕が陽にならないせいで無条件に通る）。

落ちなかったら、前提が成立していることを assert する行を足す。

## 2. issue を立てる基準

**立てる**:
- 今回の変更が生んだ、未検証のバランス/挙動リスク（例: 特定キャラとのシナジー過剰）
- 見つけたが今回のスコープ外だったバグ・不整合
- 「N試合で有意差なし」など、**試行数を増やせば結論が変わる**保留事項

**立てない**:
- 今このコミットで直したもの
- 好み・体裁の話（日記の積み残しに書くだけでよい）

作成コマンド:
```bash
gh issue create --title "<短い症状>" --label "<balance|bug|ai|infra>" --body "<背景/再現/期待/検証方法>"
```
本文には **再現手順か検証コマンド**（例: `node sim/cli.js metrics --games 800 --seed 1`）を必ず入れる。
ラベルが未作成なら `gh label create` で作る。

## 3. 仕上げ

1. 日記と（あれば）issue 番号を相互に書き込む
2. `docs/diary/README.md` のエントリ一覧を更新
3. 日記だけを1コミットにする（コードと混ぜない）:
   `git add docs/diary && git commit -m "diary: YYYY-MM-DD <一言>"`

日記に残した積み残しと open issue は、`/diary-improve-loop` が拾って潰していく。
