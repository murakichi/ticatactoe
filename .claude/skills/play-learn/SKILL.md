# play-learn

**自分で指す → 気づく → ルール化 → 検証 → 採用/撤回** のループ。
**軸は「Claude が `duel.js` で実際に指すこと」。** AI 同士の大量対戦でキャラを強くする作業（環境順位・ギア/デッキ探索・AI フラグの掃引）は **`tune-top` の領分**で、ここでは行わない。このスキルが出すのは「実戦で気づいた仮説」で、検証にだけ tune-top と同じ計測器（`probe-top`）を使う。
- 仮説を立てて実装・検証に進む前に、必ず自分が指す。測定やコード読みだけで仮説を作らない。
- 事前に `probe-top` で環境順位・弱い相手を見て、何を指すか当たりをつけるのは可（ただし探索そのものを目的にしない）。
- **指す量が成果の中心**: 1回の呼び出しで最後まで指す局を複数こなし、局面・判断・AIの動きを `docs/play/<char>.md` に残す。仮説が採用に至らなくても、対局記録は価値として残す。
- 数局の勝ち負けは採用の根拠にしない。採用の根拠は検証（paired seed の大量対戦）だけ。

## 道具

### 対局ドライバ `sim/duel.js`(ブラウザ不要・ステートレス)
状態はファイルに持ち、呼ぶたびに最初から再生する(seed 固定なので相手AIの手も含め再現)。

```bash
F=<scratchpad>/g.json
node sim/duel.js new $F --me magician --opp giant --seat 0 --seed 7 \
     [--gears a,b] [--deck 0,3,...12枚] [--size N] [--oppVaried] [--oppGears ..] [--oppDeck ..]
node sim/duel.js show $F                       # 盤(マス番号つき)・手札とコスト・固有スキル・直前の相手AIの動き
node sim/duel.js do   $F "s ignite" "p 6" "p 9" # 操作を順に実行。不正な操作はそこで止まり理由が出る
node sim/duel.js log  $F                       # 全履歴(日記・メモ用)
node sim/duel.js ai   $F [--mod ai.new.js]     # 「既定AIならここで何をするか」を表示(保存しない)
```
**見落とし防止**: `show` が相手の勝ち手（✅自分の勝ち手 / ⚠相手の勝ち手。ライフ0の自駒の奪取と、着手後の減衰・毒で奪える駒も含む）を表示し、`p N` は「置いた後に相手の勝ち手が残る」と止まる（承知の上なら `p! N`）。毎手番、まず `show` の ⚠ を読むこと。
操作: `p N` 着手 / 待ち状態(ロック・トークン先・攻撃対象)ではその対象マスの指定、`h IDX` 手札の札を使う、`s NAME` 固有・常設スキル、`lock IDX` 札を次手番に固定、`shuffle`、`charge`。
**1手番 = `h`/`s` を好きなだけ + 最後に `p`(着手)**。`p` で相手AIが自動で応答し、自分の手番に戻って止まる。
後手は `--seat 1`(開始時に相手が先に指している)。**先後を交互に**遊ぶ。
sim 未実装の札(慈雨49・縮地50・写し身51・追い剥ぎ52・福引59)は `[sim未実装]` と出て撃てない(本番では撃てる。測定の限界として扱う)。

### 検証用の計測器 `sim/probe-top.js`（tune-top のもの。詳細・採用基準は tune-top スキルを参照）
実戦で出た仮説1つを確かめるときだけ使う。ギア/デッキの近傍探索（`--scan`）は tune-top の仕事なので、ここでは回さない。
```bash
node sim/probe-top.js --target <char> --flags myRule=1 --games 200 --seed 3      # AIフラグ候補（対象席だけ）
node sim/probe-top.js --target <char> --opp <相手> --flags myRule=1 --games 300   # 穴が出た相手に絞る
```

## 手順

### 0. 準備(読む)
- **まず `docs/play/LEDGER.md`**（検証済みの全記録と「未試行の候補」）と `docs/play/<char>.md`。ここに無い案だけが「未試行」。
- `docs/tune/<char>.md` と `docs/tune/LEARNINGS.md`(過去に試して不採用になった案。**同じ案を再発明しない**)、`docs/characters.md`(ルール・固有スキル)、`docs/play/<char>.md`(前回のプレイメモ。無ければ作る)。
- 対象キャラ(引数。英語IDに読み替え)と相手を決める。相手は環境上位 + 苦手そうなキャラを含め、毎回違うものを混ぜる。

### 1. ギア・デッキを自分で決める
- 推奨のままで始めず、**盤面でどう勝つかの筋書き**から選ぶ(例: 「早期にバッズで魔力を稼ぎ、ロックで守って爆発」)。ギアは `sim/gear.js` の `GEAR_PARAMS` と `docs/characters.md` の説明、デッキは `sim/deck.js` の `SKILL_CATALOG`(idx → 札)。
- `docs/tune/<char>.md` の推奨・不採用の記録は参考にしてよいが、**最終的に選ぶのは自分**。選んだ理由を1行メモする。構成の機械的な探索（`--scan`）は tune-top の仕事。

### 2. 対局する（最後まで指す局を3局以上、先後交互、seed と相手を変える。**省略不可・このスキルの中心**）
**この手順を飛ばして手順3以降に進んではならない。** 自分で `duel.js` の `do` を呼んで指した局が1局も無い回は、仮説を台帳に書くだけで、実装・測定には進まない。台帳の行には、根拠にした対局の設定(seed・席・ギア・デッキ)と手番番号を必ず書く。
各手番で次を意識して**考えを書きながら**指す(メモは `docs/play/<char>.md` に残す):
- **置くマス**: そのマスは何本の4連ライン(行・列・斜め、4マス窓)に乗るか。自分のリーチ・相手のリーチを何本作る/消すか。相手の次の手で奪取(ライフ0の駒)されないか。氷結・ロック・火炎・帯電・式神など盤上効果の位置関係。
- **スキルを使う局面**: 魔力を使うと何が変わるか(リーチ数、相手の脅威、次手番の魔力)。**使わず貯める**判断も記録。3枠の手札から、ロック(`lock`)で次に残す札。
- **既定AIとの差**: 迷った局面で `duel.js ai` を打ち、既定AIが別の手を選ぶなら、どちらが良いかを理由つきで書く。
- 相手AIの**癖と穴**(同じ失敗を繰り返す、勝てる手・コンボを撃たない、脅威を見落とす、魔力を貯めたまま使わない、撃つべきでないスキルを撃つ)を `log` と各手番の盤から拾う。**対局中に気づいた穴は必ずその場でメモする**（手番番号・盤・AIがした手・取るべきだった手）。

負けたら、**どの手番が分岐点だったか**を特定する(`log` の手番番号 + その時点の盤)。勝ったら、**AIでも再現できる勝因**かを疑う(相手AIの癖頼みか)。

### 2.5 AI側の穴を仮説にする（対戦中に見つけたものは必ず扱う）
全席のAIは同じ実装（`sim/ai.js` ⇔ `AIPlayer.ts`）なので、**相手AIの穴 = 自分が使うときの穴**でもある。穴を見つけたら:
1. **再現**: `duel.js` の同じ設定・操作列で穴の局面まで再生し、AIの手を確認する（`duel.js ai` や `log`）。相手側に試作フラグを渡すには `new` の `--oppFlags k=v`。
2. **修正案をフラグで実装**し、穴が埋まったことを同じ局面で確認（相手AIが取るべき手を取る）。
3. **測定**: 穴を埋めた側を `--target` にして `probe-top.js` で測る（穴の出るマッチアップ `--opp` と環境全体の両方）。
4. 採用基準・ミラー・台帳の扱いは手順4〜6と同じ。台帳の「種別」に `AIの穴` と書く（自分の戦略は `戦略`）。
- 穴が **人間相手には起こりにくい悪用（AIの癖頼み）** なら、穴埋めではなく「観察」として記録だけにする。AI自身の勝ち筋・取りこぼし・無駄撃ちの修正は採用してよい。

### 3. 未試行の戦略を考える → ルール化(仮説1つ)
- **仮説の出どころは3つ**: (a) 今回のプレイで気づいた自分の戦略、(a') 手順2.5のAI側の穴、(b) `LEDGER.md` の「未試行の候補」と、台帳・LEARNINGS を読んだうえで**自分で新しく考えた、まだ試していなくて有効と思われる戦略**。
  (b)の場合も、**候補を1つ選んで、その局面を `duel.js` で実際に作って指して**確かめてから実装する（プレイせずにコード読みと AI 対 AI の `probe-top` だけで進めるのは禁止。`probe-top` は手順4の採用判定のための道具で、仮説を得る手段ではない）。
- 考えた案は、試す前でも必ず「未試行の候補」に追記する（見立てと、試す前に確認することも）。
気づきを、**AIが盤面から判定できる条件 + 取る手**の形にする。例:
> 「相手に2本以上リーチが無く、自分の魔力 ≥ X で、ロックを掛けられるマスが自分リーチの4つ目なら、トークンより先にそのマスをロックする」
- 条件が曖昧(「いい感じのとき」)なら、まだ仮説ではない。述語に落とせるまで詰める。
- `LEARNINGS.md` に同じ案・類似案が不採用で載っていたら、**何が違うか**を書けない限りやらない。
- 「置くマス」の知見は、`getEnhancedBestMove` の評価(`evaluateBoard` の重み、候補手の順序、探索深さ)として表現できないかまず検討する。スキルの使い方は `chooseSkills`/`chooseLocks`、ギア・デッキは推奨構成の変更。

### 4. 実装 → 検証（採用基準・多重比較の扱いは tune-top に従う）
1. `sim/ai.js` に**フラグ `F.<name>`(既定オフ)**で実装(既存の `F.xxx` / `AI_DEFAULTS` の流儀に合わせる)。オフで従来と結果が完全一致することを確認。
2. `probe-top.js --target <char> --flags <name>=1 --games 100 --seed S` で基準と比較(seed を変えて 100→200→400 と絞る)。差が標準誤差の約2倍以内なら採用しない。多数の案を試したなら多重比較を意識する。
3. **相手を変えて頑健性**を見る(`--envDeck varied`、`--oppGears lastStand`、上位3相手だけ、全キャラ)。特定の相手にだけ効く場合は、その相手を判定条件に入れた形で採用するか、不採用にする。
4. 実際に自分が指した局面を再現するテスト(`sim/engine.test.js` 等)を、**ルールを外すと落ちる**形で足す。

### 5. 採用 / 撤回
- **採用**: フラグを既定オンにし(または推奨ギア/デッキを更新)、`src/components/game/AIPlayer.ts`(ギア/デッキは `gear.ts`/`deck.ts`)に**同じ変更をミラー**、`AIPlayer.test.ts` に回帰テスト。`npm test -- --watchAll=false` と `node sim/*.test.js` を通す。本番AIで未計測なら、そう明記する。
- **撤回**: フラグとコードを消す(残すのは記録だけ)。

### 6. 台帳に必ず残す（採用・不採用・保留のどれでも。省略不可）
- `docs/play/LEDGER.md` の「検証済み」に1行追加（列は `docs/play/README.md`）。**再現できるコマンド・seed・基準値と候補値・標準誤差**を書く。未試行から移した案は「未試行」側から消す。
- 測定を途中で打ち切った・結論が出なかった案も「保留」として、**何を足せば決まるか**（games数・相手・seed）を書く。
- 対局ログ（`duel.js log` の要点）とAIの癖は `docs/play/<char>.md` に。
- これを書き終えるまでこの呼び出しは終わりにしない。

### 7. 記録
`/work-diary` で日記を書く。積み残し(未検証のバランスリスク・スコープ外のバグ・試行数を増やせば変わりうる保留)は**例外なく issue にも起票**し、日記に番号を残す(CLAUDE.md の Workflow に従う)。

### 8. 反映（PR → CI グリーン → master へマージ）
CLAUDE.md の許可（「PR はオーナー確認なしでマージしてよい。条件は CI がグリーンなこと」）に従う。**採用・不採用・保留を問わず、台帳・日記・スキル/ドライバの変更は master に入れる**（記録が master に無いと次回の呼び出しが再発明する）。
1. master 以外のブランチで作業する（`master` へ直接 push しない。push は GitHub Pages のデプロイを起動する）。マージ済みのブランチに積む場合は `git fetch origin master && git checkout -B <branch> origin/master` で張り直す。
2. 試験用フラグが残っていないことを確認する（不採用の案は削除済み、採用の案はミラー済み）。`git diff origin/master --stat` で意図した変更だけか見る。
3. PR を作り（テンプレがあればそれに従う）、`test` チェックが success になるまで待つ。失敗したら原因を直して push（スキップ・無効化は禁止）。
4. グリーンになったらマージ（merge コミット）。マージ後、ブランチを master に合わせ直す。

## 注意
- **プレイの勝敗を採用理由にしない**。1局は偶然で動く。採用は sim の大量対戦だけ。
- 自分が「人間として賢く指せる」手でも、AIが実装できる述語に落ちなければ採用できない。落ちないものは「観察」として記録だけ残す。
- 相手AIの既知の弱点を突く手(悪用)は、**本番の人間相手に通用するか**で価値が変わる。AIの穴を埋める修正（手順2.5）と区別して書く。
- `duel.js` は sim エンジンの忠実移植を使う。本番(Game.tsx)とのずれが疑われる挙動は、スコープ外なら issue にする。
- 状態ファイル(`g.json`)はスクラッチパッドに置く。リポジトリに入れるのは `docs/play/` の台帳とキャラ別メモ。**検証した内容を台帳に残さないまま終わらない**。
